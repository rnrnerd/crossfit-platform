# 321.cf — кроссфит-платформа

Telegram Mini App для кроссфит-соревнований: календарь стартов, заявки,
профиль атлета и проведение турнира (лидерборд, комплексы, заходы, расписание).

Backend — aiohttp + PostgreSQL, фронт — один `index.html`.

Соревновательная часть (протокол, комплексы, расписание, заходы) перенесена
из проекта `crossfit-comp`: логика подсчёта баллов — место в комплексе → баллы
за место → сумма, тай-брейк по лучшим местам. Слой сопоставления атлетов по ФИО
не переносился: здесь заходы и результаты ссылаются на заявку по id.

## Кто проводит турнир

**Платформа сама.** Свои таблицы (`wods`, `results`, `heats`, `schedule`) —
единственный источник правды: только там результат связан с заявкой, а через
неё с человеком, и только так собирается история выступлений и рейтинг сезона.

Мост во внешний модуль ниже остаётся как совместимость для событий, которые
уже идут в чужой системе. Сейчас к нему не привязано ни одного события.
Решение и его обоснование — в [BACKLOG.md](BACKLOG.md), раздел «Решено
об архитектуре».

## Связь с соревновательным модулем

Турнир может проводиться не в платформе, а во внешнем модуле (`crossfit-comp`)
со своей админкой. Тогда у события задаётся `feed_url`, и четыре турнирных
эндпоинта читают модуль по HTTP на стороне сервера, приводя ответы к своей
форме — экраны не знают, откуда пришли данные, а модуль не меняется.

Снимок всех четырёх ответов модуля кэшируется на 15 секунд: во время старта
в протокол смотрят все участники сразу, и дёргать боевой сервис на каждый
запрос нельзя. Неудача кэшируется на 5 секунд, чтобы не выстраивать очередь
к лежащему модулю. Сетевой вызов делается вне пула соединений к базе.

Привязка события и сопоставление дивизионов:

```bash
DATABASE_URL='<адрес базы>' python link_feed.py 1 https://<адрес модуля> \
    "Rx Мужчины=Продвинутые/М" "Rx Женщины=Продвинутые/Ж"
```

Пустой адрес отвязывает событие — оно вернётся к своим таблицам.

У модуля нет идентификаторов пользователей: атлеты в нём — строки ФИО.
Поэтому отметка «это вы» в его протоколе и старт-листах ставится
сопоставлением имени (нормализация регистра, «ё», латинских двойников
кириллицы, порядка слов). Это единственное место, где платформа узнаёт
человека по тексту.

Схема данных описана в [SCHEMA.md](SCHEMA.md), визуальный язык — в [DESIGN.md](DESIGN.md),
что делаем дальше и почему — в [BACKLOG.md](BACKLOG.md).

## Переменные окружения

| Переменная     | Зачем                                                             |
|----------------|-------------------------------------------------------------------|
| `DATABASE_URL` | PostgreSQL. На Railway подставляется автоматически.               |
| `BOT_TOKEN`    | Токен бота из BotFather. Нужен для проверки подписи `initData`.   |
| `WEBAPP_URL`   | Публичный адрес приложения.                                       |
| `DEV_TG_ID`    | Только для локальной разработки: вход без Telegram под этим tg_id. |
| `ADMIN_PASSWORD` | Пароль админки `/admin`. **Не задан — админка выключена целиком.** |
| `PORT`         | Порт. На Railway подставляется автоматически, локально — 8080.     |

`DEV_TG_ID` на боевом стенде задавать нельзя: он пускает в приложение
без Telegram, под чужим профилем.

## Админка

`/admin` — рабочий стол оператора: события, дивизионы, заявки, новости, клубы.
Десктопная страница, вход по паролю из `ADMIN_PASSWORD`.

Если пароль не задан, все админ-эндпоинты отвечают 403: пустой пароль пустил бы
кого угодно, поэтому по умолчанию админка закрыта, а не открыта.

Пароль уходит в заголовке `X-Admin-Password-B64` (base64 от UTF-8): заголовки
HTTP не переносят ничего вне latin-1, а пароль вполне может быть кириллическим —
браузер тогда просто откажется отправить запрос. Обычный `X-Admin-Password`
тоже принимается, он удобен для curl.

Кто и через что заходит:

- **Владелец** — `/admin`, пароль из `ADMIN_PASSWORD`. Видит всё.
- **Организатор** — `/admin`, только свои события; новости, клубы и партнёров
  не видит вовсе. Входит своей телеграм-личностью: в мини-аппе на экране «Мои»
  жмёт «Открыть админку», мини-апп выдаёт подписанную ссылку на 10 минут,
  страница меняет её на сессию на 12 часов. Общий пароль ему не нужен.
- **Судья** — в админку не входит. Отдельного судейского экрана в мини-аппе
  нет (решение 15.09.2026): результаты вносят в админке, во вкладке «Результаты».

События заводит платформа: попадание старта в каталог — её решение, а не
организатора. Организатор правит своё событие целиком.

Доступ выражен двумя декораторами над админ-хендлерами (`owner_only`
и `event_admin`); там, где хендлер и создаёт, и правит по разным путям,
стоит явная проверка `allow_event`. Её результат сравнивают с `None`,
а не проверяют на истинность: `web.Response` в aiohttp — это MutableMapping,
и пустой ответ в булевом контексте ложен.

**Готовность старта.** На вкладке «Настройки» у каждого события есть список:
организатор, категории, афиша, комплексы, заходы, расписание, судьи, заявки,
результаты. Экраны у всех стартов одинаковые — различается только наполнение,
и список показывает, чего не хватает, и ведёт туда, где это заводится. Красным
помечено то, без чего событие сломано: старт без организатора остаётся
без хозяина, и роли не на кого повесить.

## Деплой на Railway

1. Создать проект и подключить этот репозиторий — сборка идёт по `Procfile`,
   версия Python берётся из `.python-version`.
2. Добавить в проект плагин PostgreSQL. `DATABASE_URL` появится сам.
3. Задать `BOT_TOKEN`, `WEBAPP_URL` и `ADMIN_PASSWORD` в переменных проекта.
4. Таблицы создаются при первом старте — миграции идут в `init_db()`.

## Бот

Отдельного процесса бота нет: веб-сервер и отправка уведомлений живут
в одном `backend.py`.

### Уведомления

Бот пишет три письма:

- **атлету — расписку о заявке** с категорией и сроком оплаты;
- **организатору — о новой заявке.** Первая приходит сразу; если по этому
  старту письмо уже уходило в последний час, новые заявки копятся в одно
  отложенное (`send_after`), и через час приходит сводка «Новые заявки: N»
  со списком. На большом старте это одно сообщение вместо сотни. Судьям
  не пишем, свою заявку организатору не присылаем;
- **атлету — «Заявка снята»**, когда срок оплаты прошёл, а отметки об оплате
  нет. В письме срок и телеграм организатора: если деньги уже ушли, он вернёт
  заявку. Проверка раз в час; `dedup` не даёт написать дважды о том же сроке.

Напоминаний о заходах и рассылки результатов нет и не планируется — решение
14.09.2026: время захода и результаты атлет смотрит в приложении сам.

Письма не отправляются из обработчика заявки: они кладутся в таблицу
`notifications`, а фоновая задача раз в пять секунд забирает ожидающие и шлёт
их через Bot API. Подача заявки не ждёт Telegram и не падает вместе с ним,
а по статусу видно, что дошло:

| статус | что значит |
|---|---|
| `pending` | ждёт отправки; сетевой сбой или 429 оставляют его здесь, до пяти попыток |
| `sent` | доставлено |
| `blocked` | 403: человек не запускал бота или заблокировал его — повторять бессмысленно |
| `failed` | 400 (ошибка в тексте) или пять неудачных попыток подряд |
| `skipped` | пока письмо ждало, человек выключил уведомления — снято, не отправлено |

**Бот пишет только тем, кто сам входил в приложение через Telegram** —
то есть чья подпись `initData` хоть раз проверилась (`users.tg_verified_at`).
Причина не формальная: сгенерированным сидом и `fill_event` пользователям
`tg_id` выдавались подряд после настоящего и могут принадлежать посторонним
людям. Без этой проверки «Новая заявка — Павел Ольховик» ушла бы чужому
человеку, если демо-пользователь оказался организатором.

Даже проверенному бот не может написать первым: кто ни разу не нажимал
«Старт», получит `blocked`. Выключатель «Уведомления в боте» — в профиле,
`users.notify`.

Кнопка «Открыть» — типа `web_app` и ведёт на `WEBAPP_URL/?event=<id>`.
Ссылка `t.me/бот?startapp=` не годится: она открывает мини-апп, только если
в BotFather включён основной мини-апп, а у бота он выключен — нажатие вело бы
в чат, а не на событие.

**Локально в `.env` стоит боевой токен бота.** DEV-вход идёт без `initData`
и проверенным не становится, поэтому под `DEV_TG_ID` бот не пишет никому.
Но если на локальный сервер зайдут через настоящий Telegram (например, через
туннель), сообщения уйдут по-настоящему. Проверки делайте в процессе, без
`main()`: там не заводится воркер отправки.
Бот нужен как точка входа и как источник `BOT_TOKEN`, поэтому вся его
настройка делается в BotFather:

- `/newbot` — создать бота, получить токен;
- `/mybots` → бот → Bot Settings → Menu Button → задать адрес стенда.

## Демо-данные

`seed_demo.py` заливает 22 атлета, 3 события, дивизионы, заявки, комплексы,
результаты и заходы. Требует Pillow (генерирует аватарки и баннеры), поэтому
в `requirements.txt` его нет — запускать локально, указав нужную базу:

```bash
DATABASE_URL='<адрес базы>' python seed_demo.py
```

## Локальный запуск

```bash
pip install -r requirements.txt
DATABASE_URL='postgresql://localhost/crossfit_platform' DEV_TG_ID='<ваш tg_id>' python backend.py
```
