# Кроссфит-платформа

Telegram Mini App для кроссфит-соревнований: календарь стартов, заявки,
профиль атлета и проведение турнира (лидерборд, комплексы, заходы, расписание).

Backend — aiohttp + PostgreSQL, фронт — один `index.html`.

Соревновательная часть (протокол, комплексы, расписание, заходы) перенесена
из проекта `crossfit-comp`: логика подсчёта баллов — место в комплексе → баллы
за место → сумма, тай-брейк по лучшим местам. Слой сопоставления атлетов по ФИО
не переносился: здесь заходы и результаты ссылаются на заявку по id.

## Связь с соревновательным модулем

Турнир может проводиться не в платформе, а во внешнем модуле (`crossfit-comp`)
со своей админкой. Тогда у события задаётся `feed_url`, и четыре турнирных
эндпоинта читают модуль по HTTP на стороне сервера, приводя ответы к своей
форме — экраны не знают, откуда пришли данные, а модуль не меняется.

Снимок всех четырёх ответов модуля кэшируется на 15 секунд: во время старта
в протокол смотрят все участники сразу, и дёргать боевой сервис на каждый
запрос нельзя. Неудача кэшируется на 5 секунд, чтобы не выстраивать очередь
к лежащему модулю. Сетевой вызов делается вне пула соединений к базе.

Привязка события и сопоставление дивизионов:

```bash
DATABASE_URL='<адрес базы>' python link_feed.py 1 https://<адрес модуля> \
    "Rx Мужчины=Продвинутые/М" "Rx Женщины=Продвинутые/Ж"
```

Пустой адрес отвязывает событие — оно вернётся к своим таблицам.

У модуля нет идентификаторов пользователей: атлеты в нём — строки ФИО.
Поэтому отметка «это вы» в его протоколе и старт-листах ставится
сопоставлением имени (нормализация регистра, «ё», латинских двойников
кириллицы, порядка слов). Это единственное место, где платформа узнаёт
человека по тексту.

Схема данных описана в [SCHEMA.md](SCHEMA.md), визуальный язык — в [DESIGN.md](DESIGN.md),
что делаем дальше и почему — в [BACKLOG.md](BACKLOG.md).

## Переменные окружения

| Переменная     | Зачем                                                             |
|----------------|-------------------------------------------------------------------|
| `DATABASE_URL` | PostgreSQL. На Railway подставляется автоматически.               |
| `BOT_TOKEN`    | Токен бота из BotFather. Нужен для проверки подписи `initData`.   |
| `WEBAPP_URL`   | Публичный адрес приложения.                                       |
| `DEV_TG_ID`    | Только для локальной разработки: вход без Telegram под этим tg_id. |
| `ADMIN_PASSWORD` | Пароль админки `/admin`. **Не задан — админка выключена целиком.** |
| `PORT`         | Порт. На Railway подставляется автоматически, локально — 8080.     |

`DEV_TG_ID` на боевом стенде задавать нельзя: он пускает в приложение
без Telegram, под чужим профилем.

## Админка

`/admin` — рабочий стол оператора: события, дивизионы, заявки, новости, клубы.
Десктопная страница, вход по паролю из `ADMIN_PASSWORD`.

Если пароль не задан, все админ-эндпоинты отвечают 403: пустой пароль пустил бы
кого угодно, поэтому по умолчанию админка закрыта, а не открыта.

Пароль уходит в заголовке `X-Admin-Password-B64` (base64 от UTF-8): заголовки
HTTP не переносят ничего вне latin-1, а пароль вполне может быть кириллическим —
браузер тогда просто откажется отправить запрос. Обычный `X-Admin-Password`
тоже принимается, он удобен для curl.

Чего в админке пока нет и почему:

- **Комплексы, расписание, заходы, результаты.** Для стартов, привязанных
  к внешнему модулю, они ведутся в нём — второй редактор создал бы два
  источника правды. Для стартов на своих данных редактор ещё предстоит
  сделать — задачи #4 и #5 в [BACKLOG.md](BACKLOG.md).
- **Роли организаторов.** Сейчас один оператор с паролем. Таблица `event_staff`
  с ролями `organizer` / `judge` уже есть, доступ по ним включается, когда
  появятся реальные организаторы — задача #7.

## Деплой на Railway

1. Создать проект и подключить этот репозиторий — сборка идёт по `Procfile`,
   версия Python берётся из `.python-version`.
2. Добавить в проект плагин PostgreSQL. `DATABASE_URL` появится сам.
3. Задать `BOT_TOKEN`, `WEBAPP_URL` и `ADMIN_PASSWORD` в переменных проекта.
4. Таблицы создаются при первом старте — миграции идут в `init_db()`.

## Бот

Отдельного процесса бота нет: `backend.py` поднимает только веб-сервер.
Бот нужен как точка входа и как источник `BOT_TOKEN`, поэтому вся его
настройка делается в BotFather:

- `/newbot` — создать бота, получить токен;
- `/mybots` → бот → Bot Settings → Menu Button → задать адрес стенда.

## Демо-данные

`seed_demo.py` заливает 22 атлета, 3 события, дивизионы, заявки, комплексы,
результаты и заходы. Требует Pillow (генерирует аватарки и баннеры), поэтому
в `requirements.txt` его нет — запускать локально, указав нужную базу:

```bash
DATABASE_URL='<адрес базы>' python seed_demo.py
```

## Локальный запуск

```bash
pip install -r requirements.txt
DATABASE_URL='postgresql://localhost/crossfit_platform' DEV_TG_ID='<ваш tg_id>' python backend.py
```
