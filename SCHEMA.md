# Платформа кроссфит-ивентов — модель данных (черновик на обсуждение)

Цель: движок, на котором любой организатор проводит своё событие сам.
Личные и командные форматы, самостоятельная регистрация атлетов, один общий бот.

Главный принцип: **результаты привязаны к заявке, а не к человеку.**
Заявка — это участник соревнования: один атлет или команда. Благодаря этому
командные форматы не требуют отдельной ветки логики.

---

## Люди

### `users` — единый профиль человека
| поле | смысл |
|---|---|
| `id` | внутренний идентификатор |
| `tg_id` | Telegram ID, уникальный — вход без паролей |
| `name` | ФИО |
| `gender` | М / Ж — нужно для дивизионов |
| `birth_date` | для возрастных дивизионов (Мастера 35+) |
| `city`, `gym` | город и зал (для сообщества) |
| `height_cm`, `weight_kg` | параметры атлета, нужны организатору и в протоколе |
| `club_id` | клуб из справочника. **NULL = независимый атлет**, а не «не заполнено» |
| `photo`, `photo_v` | фото профиля, версия для сброса кэша |

Один профиль на все события: фото и ФИО вводятся один раз.
Это убирает ручное сопоставление имён, с которым мучились на «Херсонесе».

### `clubs` — справочник клубов
| поле | смысл |
|---|---|
| `id` | |
| `name`, `city` | |
| `is_active` | скрытый клуб не предлагается в профиле, но остаётся у тех, кто его выбрал |

«Независимый атлет» строкой в справочнике не заводим: это отсутствие клуба.
Иначе появится две записи об одном и том же — пустая и «независимый», — и
отчёты организатора начнут расходиться.

---

### `notifications` — очередь писем в боте
| поле | смысл |
|---|---|
| `user_id` | кому |
| `kind` | `entry_created` — расписка атлету · `entry_new` — новая заявка организатору (или сводка) · `entry_released` — заявка снята за неоплату |
| `text`, `link` | текст в HTML-разметке Telegram и параметр кнопки «Открыть» (`event_12`) |
| `status` | `pending` · `sent` · `blocked` (403, бот не запущен) · `failed` · `skipped` (уведомления выключили, пока письмо ждало) |
| `tries`, `error` | число попыток и последний ответ Telegram |
| `send_after` | не отправлять раньше: сводка организатору не чаще раза в час на старт |
| `meta` | что собрано в сводку: `{"entries": [id, …]}` — новые заявки дописываются в ожидающее письмо |
| `dedup` | уникальный ключ письма, повтор не кладётся: `unpaid:<заявка>:<человек>:<срок>` |

Письма не шлются из обработчиков напрямую: строка со статусом переживает
сбой Telegram и деплой посреди отправки. Выключатель — `users.notify`;
при выключенном письмо просто не кладётся в очередь.

Письмо кладётся только тому, у кого есть `users.tg_verified_at` — момент,
когда подпись `initData` впервые проверилась. У сгенерированных пользователей
её нет никогда, и это главное: их `tg_id` могут принадлежать посторонним.

## Событие

### `events`
| поле | смысл |
|---|---|
| `id`, `slug` | slug для ссылки-приглашения |
| `title`, `description` | |
| `city`, `venue` | место проведения |
| `date_start`, `date_end` | |
| `status` | черновик → регистрация → идёт → завершено → архив |
| `reg_opens_at`, `reg_closes_at` | окно регистрации |
| `visibility` | в каталоге / только по ссылке |
| `feed_url` | адрес внешнего соревновательного модуля. Задан — протокол, комплексы, расписание и заходы читаются оттуда, а не из своих таблиц |
| `banner` | афиша 16:9 (1600×900) — **контент**, идёт во всю ширину экрана |
| `mark` | квадратный знак 1:1 (512×512, PNG с прозрачностью) — **контент**, показывается кругом 56px рядом с названием |

**Оформление интерфейса всегда единое, платформенное.** Организатор приносит
контент (название, афишу, знак, описание, комплексы), но не влияет на цвета и
компоненты — это идентичность платформы. Интерфейс держат нейтральным именно
поэтому: цветной хром спорил бы с каждой второй афишей.

### `event_staff` — кто что может
| поле | смысл |
|---|---|
| `event_id`, `user_id` | |
| `role` | `organizer` — всё в своём событии · `judge` — только ввод результатов |
| `is_creator` | пометка «кто заводил событие», не замок |

Заменяет один общий пароль: владелец находит человека по имени, `@username`
или `tg_id` и назначает роль; тот открывает мини-апп и сразу видит свой старт
в разделе «Работа на стартах». Убрал из списка — доступ пропал.

Отдельного входа судье не заводим: он приходит из мини-аппа, и Telegram уже
сказал, кто он, — остаётся посмотреть, звали ли его на это событие.
Организатору для десктопной админки выдаётся подписанная ссылка из мини-аппа:
`initData` живёт внутри клиента Telegram, а `/admin` открывается в браузере. Назначить
можно только того, кто хотя бы раз открывал приложение: до этого строки
в `users` нет и роль связывать не с чем.

Единственный инвариант при снятии — **организатор должен остаться хотя бы
один**. Запрет снимать «создателя» был бы строже и бесполезнее: передать старт
его настоящему организатору — законная операция.

**Судья** не может удалять атлетов и комплексы, менять шкалы баллов и настройки —
только вносить и править результаты. Это защита от случайного клика в разгар события.

### `divisions` — дивизионы события

Если событие привязано к внешнему модулю, у дивизиона заполняются
`feed_category` и `feed_gender`: модуль односоставный и знает не id дивизиона,
а пару «категория + пол». Пустая часть ключа означает «любой» — комплекс
«для Продвинутых» без указания пола относится и к мужскому, и к женскому
дивизиону. Дивизион без сопоставления в протокол модуля не попадает.

Вместо захардкоженных «Новички/Любители/Продвинутые».

| поле | смысл |
|---|---|
| `id`, `event_id`, `name` | «Rx Мужчины», «Пары микс», «Мастера 35+» |
| `team_size` | 1 = личный зачёт, 2+ = команда |
| `gender_rule` | любой / только М / только Ж / микс (для команд) |
| `age_min`, `age_max` | для возрастных дивизионов |
| `max_entries` | лимит заявок |
| `order` | порядок отображения |

## Участники соревнования

### `entries` — заявка (ключевая сущность)
| поле | смысл |
|---|---|
| `id`, `event_id`, `division_id` | |
| `team_name` | название команды; для личной заявки пусто |
| `status` | `active` сразу после подачи (подтверждение не требуется) · `withdrawn` — снялся |
| `bib` | стартовый номер |
| `is_finalist` | прошёл в финальную стадию |

### `entry_members` — состав заявки
| поле | смысл |
|---|---|
| `entry_id`, `user_id` | для личной заявки — одна строка, для пары — две |
| `is_captain` | контактное лицо команды |

Атлет может подать несколько заявок на одно событие (например, личный зачёт
и командный) — это просто разные `entries`.

## Соревновательная часть

### `wods` — комплексы
| поле | смысл |
|---|---|
| `id`, `event_id`, `name`, `description`, `order` | |
| `result_type` | время / повторения / вес / очки |
| `time_cap` | лимит |
| `day` | день проведения |
| `stage` | квалификация · полуфинал · финал |
| `points_table` | своя шкала баллов (как сделали для «ФИНАЛА») |
| `tiebreak_note` | что считать при равенстве |

### `wod_divisions` — какие дивизионы выполняют комплекс
Связь многие-ко-многим. Заменяет нынешние списки категорий строкой.

### `results` — результаты
| поле | смысл |
|---|---|
| `entry_id`, `wod_id` | привязка к заявке, а не к человеку |
| `value` | сырой результат (секунды / кг / повторы) |
| `tiebreak_value` | доп. критерий при равенстве |
| `status` | зачтён · не финишировал · не вышел · закрыт по кап-у |
| `judged_by`, `judged_at` | кто из судей внёс — важно при спорах |

Баллы **не хранятся** — считаются на лету из мест внутри дивизиона.
Так уже работает сейчас: правка шкалы мгновенно пересчитывает лидерборд.

## Правила подсчёта (решено)

**Место в комплексе** — среди заявок своего дивизиона, у кого есть результат.
Равные результаты делят лучшее место, следующий перепрыгивает (1, 1, 3).

**Баллы за место** — по шкале комплекса; если своя шкала не задана, обычная
формула `100 − 5 × (место − 1)`.

**Итог = сумма баллов по всем комплексам, включая финальные.** Квалификация и
финал не разделяются: у финалистов просто больше комплексов с результатами.
Кто не прошёл в финал — остаётся с баллами за квалификацию.

**Равенство суммы → выше тот, у кого лучше место.** Сравниваем списки мест,
отсортированные по возрастанию: у кого выше лучшее место — тот впереди; при
равенстве смотрим следующее по списку, и так далее.

> Пример: у A места 1, 5, 10; у B — 3, 4, 9. Суммы равны.
> Лучшее место: A = 1 против B = 3 → **A выше**.

**Нет результата** (не вышел, снялся) — 0 баллов, в распределении мест не участвует.

## Режим судьи (ввод с телефона)

Отдельный экран в том же боте, оптимизированный под площадку:

1. **«Мои заходы»** — ближайшие по времени, а не вся админка.
2. Старт-лист захода **с фото и дорожками** — быстро опознать атлета в шуме.
3. Тап по атлету → крупное поле с маской (`мм:сс` / кг / повторы) и кнопки
   **DNF**, **не вышел**, **кап**.
4. Сохранение → лидерборд у зрителей обновляется в течение 5 секунд.

**Плохая связь.** Введённое не теряется: остаётся на экране с пометкой
«не отправлено» и кнопкой повтора. Бумажки остаются страховкой — оператор
всегда может добить вручную.

**Двойной ввод.** Если результат внесли и судья, и оператор — побеждает
последнее значение, но видно «изменено: Иванов, 14:32» (поля `judged_by`,
`judged_at`). При спорах сразу понятно, кто что вносил.

**Назначение на заходы** пока не делаем: судья видит все заходы события и сам
выбирает нужный. Меньше настройки для организатора.

### `heats` — заходы
`id`, `event_id`, `wod_id`, `number`, `day`, `briefing_start/end`, `start_time`, `location`

### `heat_entries` — кто в заходе
`heat_id`, `entry_id`, `lane`

### `schedule` — расписание
`id`, `event_id`, `day`, `time`, `title`, `location`, `division_id` (необязательно)

## Проверка на сценариях

**1. «Битва за Херсонес» (как было).**
Событие → 6 дивизионов (3 уровня × 2 пола, `team_size = 1`) → заявки на одного
человека → комплексы с привязкой к дивизионам → результаты. Ложится один в один,
старые данные можно импортировать как историческое событие.

**2. Командный ивент.**
Дивизион «Пары микс»: `team_size = 2`, `gender_rule = микс`. Заявка = команда,
в составе два человека. Результат вносится один на команду. Лидерборд считается
так же, как личный.

**3. Квалификация и финал.**
Комплексы помечены стадиями. После квалификации отмечаем прошедших
(`is_finalist`), финальные комплексы считаются только среди них — как было
с 12 финалистами.

**4. История атлета.**
Все его заявки по всем событиям → результаты и места. Отсюда вырастают профиль,
рейтинг и «мои соревнования».

## Решено

- Роли: **организатор** и **судья** (судья вносит результаты с телефона).
- Регистрация атлета — **самостоятельная и автоматическая**, без модерации.
- Итог — **сумма баллов по всем комплексам**, квалификация и финал вместе.
- Равенство суммы — **выше тот, у кого лучше место**.
- Командные форматы — заложены с самого начала (заявка = 1 человек или команда).
- Один общий бот платформы, брендинг организатора внутри события.

## Открытые вопросы (не блокируют старт)

1. **Изменение состава команды** после регистрации — разрешаем и до какого момента?
2. **Оплата участия** — вне платформы (организатор сам) или внутри.
3. **Отбор в финал** — организатор отмечает финалистов вручную или система
   предлагает топ-N по сумме баллов автоматически.
4. **Модель оплаты платформы** организаторами — за событие, за участника
   или подписка. На схему не влияет, решается позже.
